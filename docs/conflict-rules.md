# Phase 2: conflict and history rules

24 November 2026. Depends on the completed Phase 1 assumptions. This document selects a business arbitration policy; it does not verify Salesforce capabilities. Scope is field conflict semantics and worked outcomes. Database transactions, webhook handling, job states, scheduling, and outage coordination remain Phases 3–6.

## 1. Canonical edits and trusted metadata

A logical edit has `editId`, `tenantId`, canonical entity ID, `origin` (PORTAL or SALESFORCE), `sourceRevision`, `occurredAt`, stable `actorId`, and a changed-field patch. IDs are scoped to tenant/source. A source revision is a strictly increasing committed record revision within a stable source record incarnation; never compare revisions numerically across sources. All fields in one edit share its revision/time. Source revision resets or reused IDs violate this contract and require explicit remapping, not silent comparison. Keep raw source metadata and local `receivedAt` separately.

For portal saves, derive actor from authenticated identity; ignore body `editedBy` as authority. Serialize saves per canonical record, allocate a revision and immutable edit ID, assign server commit time, and durably record the edit and outbound intent together. A retried portal save must carry the same client request key scoped to authenticated principal/entity; reusing that key with different content is an error. A new save with a new key is a distinct edit even if the value is equal. Source commit time means the server-assigned timestamp at the serialized commit boundary, not browser time or delivery time. Phase 3 must make the ordering/durability boundary precise.

Salesforce source metadata must be authenticated and replay-stable. `changedBy` display email is retained, but stable principal ID is preferred. Do not replace missing attribution with an invented human actor. A source event containing integration propagation has a transport `eventId` and remote record revision, but its propagated fields refer to the original logical edit ID/version. An integration write does not become a new human edit at the later remote timestamp.

## 2. Deterministic field comparison

For each field maintain **two source candidates**: the latest original edit to that field from PORTAL and the latest original edit from SALESFORCE. Missing candidates are empty. Initial bootstrap values have a separately identified baseline below all captured edits; they do not invent historical edits.

1. Within a source, choose the edit with greatest `sourceRevision` that explicitly edits this field. An older event can still advance another field whose latest revision is older. Record-level revision alone must never discard the whole patch.
2. Between the two source candidates, compare the tuple `(occurredAt UTC epoch milliseconds, originRank)` lexicographically. PORTAL rank = 1, SALESFORCE rank = 0; greater wins. This arbitrary, explicit tie preference makes the portal's finance correction win an exact timestamp tie. Client agreement remains required.
3. A single source revision identifies one immutable record commit. Conflicting content or two distinct edit IDs claiming the same source revision are contract errors to quarantine, not an occasion for a random tie-break. Equal edit identity and identical canonical content are duplicate delivery.

The current value is the winning candidate's set/clear value, with its logical edit ID and comparison metadata. Never compare delivery time, worker run time, replay cursor, actor email, or remote integration-application revision to decide human-edit precedence.

This is a two-stage policy, not pairwise timestamp last-write-wins over every historical edit. Keeping only the current overall winner is insufficient: a later same-source revision can have an earlier timestamp after clock rollback and change the cross-source outcome. Retain both source candidates and recompute. Source candidates merge by maximum source revision, independently of event arrival order; winner selection is a deterministic function of those candidates. Do not implement “same source uses revision, otherwise timestamp” as a single pairwise comparator: that relation can be non-transitive.

With +/-1 second clock uncertainty per source, cross-system physical order is unknown within up to 2 seconds. Timestamp arbitration is a defensible business rule, not proof of the actual last human action. We do not use an approximate-equality window, which can introduce non-transitive comparisons. A substantial clock anomaly is visible for remediation and invalidates timing assumptions; already observed source times are never rewritten to make a desired winner. A later human correction is a new attributed edit.

Omitted keys make no candidate/history field entry. Explicit nullable `null` is a real clear competing exactly like a set. A full record requires a trustworthy change mask or attributable field versions/history; absent that metadata, do not fabricate edits by snapshot diffing.

## 3. History and portal concurrency

Append one immutable logical edit fact and its explicit field values for every distinct edit, including equal-value, losing, late, and subsequently superseded edits. Preserve original actor, source time, source revision, and raw patch. Store transport receipt/application evidence separately: duplicate webhooks, API attempts, acknowledgments, and repair applications are not extra human edits. Same event ID with changed content is an integrity error. Replay must identify the same source edits as webhooks.

Decision evidence records candidates considered, chosen edit ID, comparison rule/version, and supersession/application results. “Won on arrival” is not a permanent property: a later edit can supersede it. Reconstruct per-source field history by source revision; do not label the portal's arrival-time old value as the source's actual previous value. If upstream old values are unavailable, retain every changed value and the known baseline; do not invent an unknown predecessor.

Two portal users may save stale forms. Accept valid changed-field patches in serialized server commit order; no optimistic stale-form rejection is selected here. Different-field patches both survive. For the same field, the higher portal revision becomes the portal candidate. The save response returns accepted edit ID, authoritative revision/time, resolved current values/winning IDs, and synchronization status. Acceptance means the edit is durably retained, not that it necessarily wins against a Salesforce candidate. A subsequent refresh shows resolved current values and history; there is no promise of immediate live UI updates. A stale whole-form submission is not a patch and must not silently reassert unchanged fields.

Each accepted portal edit has durable outbound intent. Preserve individual jobs/audit; no pending-write coalescing is enabled. Before dispatch, an obsolete or losing field may be marked superseded with its reason instead of overwriting Salesforce with a known losing value. Thus two rapid saves may produce two remote applications if both are sent before supersession, or only the final winning value if the first has become obsolete. This is stale-work suppression, not deletion of an edit or combining its history. The brief requires complete history on our side and converged current values; it does not require every losing intermediate value to become visible remotely. If both systems must contain every intermediate audit edit, a separate remote audit interface is required.

## 4. Race-safe convergence and echoes

The portal computes the resolved value. Salesforce users can temporarily see their own committed value before reconciliation; the record API is not assumed to implement our field policy. Reconciliation conditionally patches only fields that differ from the resolved winner, carrying their original logical identities. Do not overwrite unrelated fields.

Before an outbound conditional write against remote revision R, our side must have incorporated all original edits through R (via complete replay/history or an equivalent trustworthy revision-associated field-history response). A plain read of current values and a revision does not establish complete history. Obtain/confirm a bounded history boundary through R, merge its original edits, recheck local field candidates, then build the patch. Track application revisions separately from original source candidates. This strengthens Phase 1's read/conditional-write assumption: merely reading a revision cannot protect unseen edits if the worker then deliberately overwrites them. Phase 6 will specify coordination with backlog replay.

If Salesforce changes after R was read, the conditional write must fail without effect. Fetch the new revision and the intervening edit history, merge, and retry only fields still requiring correction. A local edit racing after a patch was prepared can leave a temporary older remote value; serialize our own outbound attempts per record and schedule the new winner afterward. Never hold a database transaction open while waiting on HTTPS; Phase 3 must use durable work and completion checks to close this boundary.

Classify inbound events per field:

- A verified echo references a known outbound mutation and matches its expected original edit IDs and patch. Record transport/application evidence, keep original actor/version, and do not create new human candidates. A delayed echo cannot roll back newer candidates.
- A genuine source edit, including one by an integration account without matching provenance, updates its source candidate and history normally.
- If an inbound human edit loses but has changed Salesforce away from the winner, persist necessary repair intent. If it wins, update the portal; patch other divergent fields only if needed. A duplicate may find existing unresolved repair work, but must not create unlimited duplicate repairs.

An old echo proves only what happened at its application revision; it does not prove the remote value is current now. A repair must reconcile against fresh revision/history evidence and be keyed to desired winner versions so a duplicate receipt cannot multiply equivalent work. Mixed events need a reliable mask separating propagated fields from genuinely new edits; if provenance cannot distinguish them, the upstream contract is insufficient. Side-effect changes to allowlisted fields must be attributable distinct source edits. Unknown or mismatching correlation is not blindly suppressed.

Each attempted write costs one outbound request. A stale-precondition failure followed by one read, one history page, and one successful retry costs **4 requests** total, not one. If history needs p pages, that path costs `3 + p`; a separate lookup/read adds its own request. Repeated races repeat these costs. Normal writes may also require a read/history page if no trustworthy cached coverage through the expected revision exists. Therefore Phase 1's one-write baseline and 10 requests/s overhead are conditional on adequate metadata/coverage reuse and low contention; Phase 6 must revise them if the complete flow exceeds that allowance. Every request shares the cap, even failed attempts.

For ambiguous successful updates, retain mutation identity and expected original winner versions. Resolve through replay/correlation or idempotency status if available; otherwise a read plus complete history through its revision establishes what happened before recomputing. A retry with old precondition may fail because the first request succeeded; that is not evidence of failure to apply. Never resend a stale patch unconditionally. For creates, use the stable external UUID/atomic unique upsert or durable idempotency key from Phase 1. Resolve acceptance to the same remote ID; read/merge before updating an existing result. Repeated upsert must not reset newer remote fields. Without these capabilities, duplicate-free ambiguous creates are not guaranteed.

## 6. Convergence argument and validation limits

For a finite set of distinct original edits, retaining the greatest revision per source/field yields the same candidates under any delivery order and duplicate repetition. The fixed timestamp/rank choice yields one value for each field from those candidates. History is the set of distinct immutable edit facts, independent of whether an edit currently wins. A repair carries an existing edit identity and cannot generate a higher competing original edit, so echo processing does not perpetuate writes.

If replay eventually supplies every edit, remote revisions/conditional writes and provenance are trustworthy, mappings are resolvable, and processing/request capacity eventually exceeds arriving work, repeated reconciliation reaches the same current fields on both replicas once edits settle. Under continuous concurrent edits, temporary divergence is expected; no unconditional finite convergence or 30-second claim follows from these rules alone. Missing history, unsupported conditional writes, permanent invalid data, rate exhaustion, or missing provenance are explicit feasibility failures, not hidden guarantees.

Validation performed: manually traced A–N including reverse arrival order where applicable; reviewed same-source revision versus cross-source timestamp separation, losing/late history, duplicate identity, remote race, and echo/repair behavior against the brief and Phase 2 acceptance. This is design reasoning, not executed tests or verified Salesforce behavior. Phase 3 must preserve both source candidates and decision evidence; Phase 6 must cost revision/history coverage and recovery barriers.

Remaining client decisions: timestamp/rank policy and portal stale-save acceptance (Q05,Q07), source revisions/field-history coverage tied to remote R (Q03,Q09), provenance including mixed/side-effect fields (Q10), and history being authoritative on our side versus duplicated into Salesforce (Q21). Alternatives change comparison semantics, request amplification, or require additional upstream interfaces.
