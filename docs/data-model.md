# Phase 3: durable data model

24 November 2026. Production PostgreSQL design, dependent on `assumptions.md` and `conflict-rules.md`. This is a schema and transaction specification, not an executed migration or verified Salesforce integration. Preserve Phase 2's two source candidates per field, immutable edit facts, and original provenance. All keys, foreign keys, and queries include tenant scope; IDs below are UUIDs unless explicitly source IDs.

## 1. Tables and invariants

Use a common entity row as the locking and identity anchor. Customers and contacts have typed current-value projections. Source versions and history remain separate from those projections. Text enum names below represent constrained values, not arbitrary input.

| Table | Principal columns | Constraints and access paths |
|---|---|---|
| `entities` | `tenant_id, entity_id, kind, lifecycle, portal_revision bigint, resolution_generation bigint, created_at` | PK `(tenant_id, entity_id)`; unique `(tenant_id, entity_id, kind)` for typed child FKs; kind CUSTOMER/CONTACT. Lifecycle includes PLACEHOLDER, ACTIVE, BLOCKED. Every modifying transaction locks this row. |
| `customers` | `tenant_id, entity_id, kind=CUSTOMER, name, status, owner_principal_id` | PK and typed FK to entities; active name required; owner FK tenant-scoped to principals. No extra business fields. |
| `contacts` | `tenant_id, entity_id, kind=CONTACT, full_name, phone, email, city, owner_principal_id, customer_entity_id` | Typed entity FK; customer FK to customers; index `(tenant_id, customer_entity_id, entity_id)`. Active contact requires full name and resolved customer. Nullable optional details support explicit clears. |
| `principals`, `principal_source_ids` | Canonical principal ID, display metadata, inactive flag; source account/principal ID mappings | Unique tenant/source-account/principal-ID mapping; retain inactive identities. Edit actor and current owner are separate concepts. Unknown attribution remains explicitly unresolved, never replaced by a made-up human. |
| `source_ids` | `tenant_id, source_account, object_type, source_record_id, source_incarnation, entity_id, external_uuid` | Unique `(tenant_id, source_account, object_type, source_record_id, source_incarnation)`; unique entity/source-account/object mapping; unique non-null external UUID in tenant/account/object scope. Point lookup uses these indexes, never email/name scans. |
| `edit_facts` | `tenant_id, edit_id, entity_id, origin, source_account, source_incarnation, source_revision, occurred_at_ms bigint, actor_source_id, actor_principal_id nullable, actor_display, patch jsonb, canonical_content_hash, received_at` | PK `(tenant_id, edit_id)`; unique original commit `(tenant_id, entity_id, origin, source_account, source_incarnation, source_revision)`; index `(tenant_id, entity_id, occurred_at_ms, edit_id)` plus source revision lookup. Canonical patch preserves explicit null and omits unedited fields. Append-only. |
| `edit_fields` | `tenant_id, edit_id, field_name, operation, value jsonb` | PK `(tenant_id, edit_id, field_name)`; FK to fact. Operation SET/CLEAR; JSON null is never an absent field. Values for owner/customer retain source IDs even before canonical mapping. This normalized detail supports field audit without repeatedly scanning JSON patches. |
| `field_candidates` | `tenant_id, entity_id, field_name, origin, edit_id, source_revision, occurred_at_ms, value` | PK `(tenant_id, entity_id, field_name, origin)`; FK to edit field. Exactly one latest original candidate per source/field, selected by source revision. Both origins retained even when losing. Single active Salesforce source account/incarnation per entity is assumed. |
| `field_resolutions` | `tenant_id, entity_id, field_name, winning_edit_id nullable, baseline_id nullable, resolved_value, generation, rule_version` | PK `(tenant_id, entity_id, field_name)`; exactly one winning edit or identified bootstrap baseline. Current typed projections must match these resolutions for ACTIVE entities. Unresolved reference values remain here while lifecycle exposes blocking. |
| `baselines` | `tenant_id, baseline_id, entity_id, capture_boundary, values, imported_at, provenance` | Identified bootstrap state below captured edits; not fabricated human history. |
| `decision_log` | `tenant_id, decision_id, entity_id, generation, field_name, portal_candidate_id, salesforce_candidate_id, winning_edit_id, rule_version, reason, decided_at` | Append-only; index `(tenant_id, entity_id, generation)`; references candidate edit facts, not mutable candidate rows. Captures losing/late decisions and supersession rationale. |
| `event_receipts` | `tenant_id, source_account, event_id, canonical_content_hash, entity_id, source_revision, classification, applied_at` | PK `(tenant_id, source_account, event_id)`; original events link to edit facts through `receipt_edits`; echoes can link to multiple existing edits. Same identity/different canonical content is an integrity error. Signature/delivery timestamps are excluded from canonical content. |
| `portal_requests` | `tenant_id, authenticated_principal_id, entity_id, request_key, content_hash, edit_id, response` | Unique full request scope; persists accepted save response for retry. Different body for same key is a conflict. Allocate/reuse entity UUID before a create retry; create request scope also includes object kind. |
| `outbound_jobs` | `tenant_id, job_id, entity_id, intent_kind, initiating_edit_id nullable, target_generation, desired_versions jsonb, state, available_at, attempts, lease_owner, lease_epoch, lease_until, blocked_reason` | PK; unique portal intent per initiating edit; unique repair intent `(tenant_id, entity_id, target_generation, intent_kind)` for repairs. Partial ready index `(available_at, tenant_id, job_id)` and entity/state index. States READY, BLOCKED, LEASED, RETRY, UNCERTAIN, SUCCEEDED, SUPERSEDED, FAILED. Jobs remain individually accountable; no edit coalescing. |
| `job_fields` | `tenant_id, job_id, field_name, desired_edit_id, disposition, reason` | PK job/field; preserves per-field applied/superseded outcomes when only part of a job remains current. |
| `record_dispatch` | `tenant_id, entity_id, active_mutation_id, lease_epoch, lease_until, uncertain` | One row per entity; serializes our remote mutations. An unresolved mutation blocks newer remote writes until reconciliation establishes safe continuation. |
| `outbound_mutations`, `outbound_attempts` | Immutable mutation ID, entity/job, original edit IDs, exact patch, external UUID, expected remote revision, prepared generation; attempt ID, start/end, result/status, remote revision, ambiguity | Unique mutation ID; attempts refer to mutation, each network attempt recorded separately. Correlation survives lost responses. Secrets excluded. A materially rebuilt patch/precondition gets a new mutation ID; retrying identical idempotent content retains identity. |
| `remote_evidence` | `tenant_id, entity_id, observed_revision, observed_values, history_covered_through_revision, coverage_proof, observed_at` | PK entity. Snapshot revision alone cannot raise history coverage. Store evidence of complete history through that record revision, including applications, independently of latest original candidate revision. |
| `application_evidence` | `tenant_id, mutation_id, remote_revision, event_id nullable, applied_field_versions, evidence_kind` | Unique mutation/remote-revision/evidence-kind; records response/echo/replay confirmations without inventing human edits. Delayed evidence cannot replace a newer remote observation. |
| `replay_checkpoints`, `replay_pages` | Account/partition/epoch, committed opaque cursor, target high-water mark; page ID, predecessor/successor cursor, manifest hash, event count, completed count/status | PK stream scope; unique page identity. Pages track complete committed application, including duplicates. Only contiguous completed pages advance checkpoint. Opaque cursors are never numerically sorted. |
| `dependency_waits` | `tenant_id, entity_id, job_id nullable, dependency_kind, source_reference, state` | Unique waiter/dependency; index unresolved dependency key for waking work after mapping. Detect missing/invalid/cyclic dependencies visibly. |
| `validation_incidents` | Tenant/source identity, payload hash, bounded diagnostic, reason, first/last seen, status | Failed validation/integrity evidence, separate from accepted receipts; access-controlled and size bounded. Never counts as successful application. |
| `outbound_budget` | Account, next permitted start, throttle-until, scheduling epoch, configured cap, effective rate, last throttle/recovery step time | One shared durable serialization point for outbound roles. Phase 5 specifies sole-egress actual-start pacing and confirmed fencing before failover; no private worker token buckets. Effective-rate/cooldown persistence prevents restart bypass; a database lease alone cannot fence a paused sender. |

FKs from historical rows prevent accidental loss of referenced facts. Enforce append-only history using application privileges (no normal UPDATE/DELETE on facts/fields/decisions) and constrained maintenance procedures. Enforce field allowlists/types and source-revision/content consistency in the application transaction; cross-table winner/projection invariants cannot be expressed by simple CHECK constraints alone. No deletion cascade removes required history.

## 2. Transactions and authoritative portal ordering

Use READ COMMITTED with explicit row locks and uniqueness constraints. All entity writers lock `entities FOR UPDATE` before checking or changing candidates, resolutions, projections, jobs, mappings, or evidence. For transactions involving multiple existing entities, lock entity UUIDs in sorted order. Identity creation uses a tenant/account/object/source-ID transaction advisory lock (a hash collision only adds serialization), then source-ID unique constraints as the final arbiter. Concurrent mapping collisions roll back and retry against the existing canonical entity; never merge by contact details. Bound transaction/lock time; deadlock/serialization retries rerun the whole transaction with the same request/event identity.

**Portal save:** authenticate and validate outside the transaction; resolve identity and lock entity; check request key; allocate `portal_revision + 1`; sample database `clock_timestamp()` at this serialized decision boundary and truncate to UTC epoch milliseconds; insert immutable edit fact/fields; replace that source's affected candidates; recompute winners and append decision evidence; update typed values/lifecycle and generation; insert individual outbound intent and field dispositions; persist retry response; COMMIT before returning success. Server time means this transaction's serialized decision time, not PostgreSQL's eventual WAL commit timestamp (which is unavailable when inserting the fact). Rollback discards the allocated revision/time; acknowledged edits are durable. Clock rollback is allowed by Phase 2's source-revision rule. Never trust a browser time/actor.

**Inbound accepted event:** validate/authenticate before opening a write transaction; acquire identity/entity locks; check receipt identity/hash and immutable source commit; append distinct original facts, or verify echo provenance and record application evidence; merge per-field candidates and resolutions; update typed projection/lifecycle; add deduplicated repair/dependency intent where needed; insert accepted receipt and replay-page application marker if applicable; COMMIT; only then send 2xx. Duplicate with identical content returns success after confirming the earlier committed receipt. Unknown/mismatching provenance cannot be acknowledged as a verified echo.

**Worker claim:** short transaction selects due jobs using `FOR UPDATE SKIP LOCKED`, acquires the entity dispatch slot with a guarded update, increments lease epoch, sets owner/deadline, and commits. A claim transaction never waits on Salesforce. Multiple jobs for one entity may exist; only one mutation may be in flight. Exact ordering/fairness/backoff is Phase 5.

**Prepare/send/complete:** after complete remote history coverage through expected revision R has been merged, lock entity and dispatch state, recheck candidates and job fields, and durably store the immutable conditional mutation with original provenance and local generation. Commit before HTTPS. Every network request obtains the shared outbound budget. On response, a new transaction checks lease epoch/mutation identity, stores evidence/outcome, updates mapping for a confirmed create, and rechecks current generation. Mark fields satisfied only when supported by evidence; a newer local winner requires durable follow-up work. Never overwrite current values from an old response. A stale worker may submit evidence for reconciliation but cannot finalize a reclaimed lease.

Lease expiry is permission to investigate, not proof no remote effect occurred. Reclaim increments fencing epoch and classifies a prepared/sent mutation as UNCERTAIN; resolve it through correlation/idempotency or read plus complete history before authorizing conflicting mutations. A database fence cannot cancel a paused worker's already issued network request. Remote conditional revisions and idempotent mutation/create identities are still required. A worker must check lease before dispatch; unresolved delayed requests remain a risk unless the upstream contract safely fences/resolves them. If that cannot be established, block the record visibly rather than claim safe completion.

**Replay checkpoint:** register the source's bounded page manifest; apply each event through the same inbound transaction, marking that manifest entry complete atomically with its effect (or known committed duplicate). Lock stream checkpoint, advance through consecutive fully completed pages only, and commit the checkpoint update with the final application/completion evidence. Later pages may complete first but cannot jump a gap. Persist the upstream high-water mark and epoch; unknown retention gaps/invalid events stop advancement. A webhook receipt alone does not certify replay cursor coverage; matching manifest evidence does. Full replay scheduling and outage barriers remain Phase 6.

## 3. Create mapping and unresolved references

Portal create allocates canonical UUID, fact, projections, and intent atomically. Customer create must obtain a confirmed unique external-ID mapping before its dependent contact is dispatched. An uncertain parent create blocks contact writes until resolved. Never use repeated upsert to reset a previously created remote record's fields.

Remote create locates/allocates canonical identity and source mapping in the same application transaction; concurrent webhook/replay delivery converges through identity locks and uniqueness. Unknown update may establish a PLACEHOLDER entity plus its attributable field candidates/history, without inventing missing create values. A later create/replay fills only baseline/missing candidates consistent with source revisions. It cannot overwrite newer field edits.

For a missing customer reference, create a typed placeholder customer with source mapping, record the contact's exact reference candidate/history, and mark the contact BLOCKED until the parent is hydrated and active. The same rule preserves unknown owner source IDs while delaying the typed canonical-owner projection. During blocking, API responses expose incomplete resolved state/status; an old typed FK is not presented as the resolved current value. Do not claim these exceptions meet 30 seconds. Parent/principal mapping resolution wakes indexed waiters and transactionally materializes the latest resolved references without inventing another human edit. Parent updates do not require locking every child; bounded wake-up batches process children separately.

## 4. Crash boundaries

| Failure point | Durable state and next action |
|---|---|
| Before portal/inbound commit | No accepted partial edit, receipt, or intent. Retry the same identity. |
| After commit, before response | Edit/history/intent/receipt all exist; retry returns prior result without another logical edit. |
| After job claim, before preparation | Lease expires; reclaim and recheck current winners. |
| After preparation, before send or after send with no response | Identical durable mutation exists; treat as potentially sent and reconcile safely. Do not infer failure from missing response. |
| Remote acceptance, before local completion | Resolve original mutation/create identity; persist application/mapping and re-evaluate newer winners. |
| Completion races with new local save | Entity lock orders local decisions; generation check preserves follow-up intent. No network call holds that lock. |
| Some replay page events committed | Re-read manifest/receipt markers; dedup overlap; checkpoint stays before incomplete page. |
| Database unavailable or durable write fails | No successful save/webhook acknowledgment. Outbound dispatch pauses if it cannot durably prepare/account for work. |

Production assumes `synchronous_commit=on` and persistent PostgreSQL WAL/storage so acknowledged transactions survive an application process restart. Database-node loss, backups, and disaster recovery need an agreed failure model; they are not established by this design or the optional local demo.

## 5. Five-million-record lookup and history growth

All hot operations use tenant/source IDs, entity PKs, ready-job indexes, or per-entity field/history indexes. They do not scan five million records. With three customer fields and six contact fields, two candidate rows per field imply 30–60 million candidate rows for five million entities if both origins touched every field; resolutions add 15–30 million rows. Sparse allocation reduces this upper envelope. Source-ID mappings are approximately one Salesforce mapping per entity, plus principals and bootstrap metadata. Validate real query plans and working-set sizes before production sizing.

At peak 20 original edits/s in each direction, history grows by `40 * 86,400 = 3,456,000` edit facts/day; quiet 1/s each gives 172,800/day. Mean fields per edit k adds k times as many edit-field rows, with decision rows depending on affected fields. At an illustrative 1 KiB per original edit including its field values, raw edit content alone is about 3.30 GiB/day at sustained peak, excluding indexes, WAL, replicas, receipts, jobs, decisions, attempts, and backups. Echoes/duplicates do not add original edit facts, but add receipt/application/attempt storage. This is a sizing input, not a storage forecast; Phase 6 must budget the full footprint.

Start with indexed current-state tables and time-based archival planning for history. If partitioning facts by time, PostgreSQL partition-local uniqueness cannot silently replace global edit/source-commit uniqueness: keep an unpartitioned identity registry with global unique keys and location metadata in the same transaction, or retain the unpartitioned indexed facts until measured need justifies this complexity. Preserve entity/time audit access across archives. No required history is pruned in this exercise. Replay's 72-hour upstream retention is not local audit retention. Receipt, mutation identity, and dedup retention must cover all possible retries/replays; until a bounded retry contract is agreed, retain them. Expiring a receipt must never allow the immutable edit/source-revision uniqueness guard to disappear.

## 6. Validation and unresolved decisions

Manually traced Phase 2 cases A–N against constraints/transactions: distinct fields retain separate candidates; losing and clock-rollback edits retain both source candidates; same-value distinct revisions append facts; duplicate identities do not append facts; old echoes affect application evidence only; races/lost responses preserve durable mutation identity and follow-up work. Reviewed every crash boundary above and parent-first creation. This is design validation; no database migration, throughput test, or Salesforce capability test was run.

Open gates remain Q03/Q04/Q08/Q09/Q10 (replay, idempotency, conditional writes, provenance), Q11/Q12 (mappings/dependencies), Q17 (retention/storage), and Q21 (history location). Phase 3 clarifies server timestamp semantics and explicitly exposes blocked unresolved references without weakening history capture. Rate pacing, detailed inbound/outbound error policy, and catch-up arithmetic remain Phases 4–6.
